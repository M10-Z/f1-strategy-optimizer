## 优先发现与修复

1. **浏览器导出破坏证据哈希（高优先级客观 bug）。** 原页面用 `JSON.parse` 后再 `JSON.stringify` 下载，将 Python 的 `1.0` 等改成 `1`。原 `output/workbench-acceptance/decision-export.json` 的记录哈希、内层冻结哈希均校验失败，尽管内存测试成功。现直接下载服务器原始 JSON 文本；真实下载文件在独立 Python 进程中验证记录、冻结输入、假设及引擎版本，再逐项重算模拟。原失效下载保留，不改写冒充有效证据。
2. **选择真实时点但沿用固定四车、第 8 圈数值。** 原引擎确实支持多车、车辆速度差、固定/响应式对手与名次规划；界面没有把这些能力连接到所选前缀。现从冻结前缀选择附近有数值间距的车辆并加入队友，也可自选或选择全部登记车。边界取 ego 已完成圈数，默认再模拟 6 圈；全部参与者、排除车辆、终点、条件、情景及对手策略可见。未知输入保持 null，不能直接运行。没有未来数据进入初始化。
3. **目标名次只是风险统计，未影响旧排序。** 新界面明确目标为所选车阵内前 k 名，提供平均名次优先与保守排序。保守排序依次比较最差模型名次、未达目标的主观情景权重占比、平均名次、较少进站和标签。复用同一引擎的全部候选结果，不训练新模型；权重占比不是失败概率。敏感性沿用同一偏好，显示参数原值、修改值及方案翻转。
4. **状态变化及失败路径。** 留空数字不再通过 JavaScript `Number('')` 自动变成零；载入新选择时清空旧车辆表并禁用确认，修改运行中输入会取消旧任务。无可行方案仍展示留场的拒绝原因，明确不提供建议。窄屏长车名与条件文本已修复溢出。

前缀初始化本身仍是模型假设：已报告间距异步；当全部所选间距都有值时减去其最小值，若任一缺失则保留原参考、等待手工补齐。胎龄/配方取可见前缀；车辆基础圈时 = 前缀中位数 − 用户假设的下一圈轮胎贡献，避免将胎耗重复叠加，但不代表分离出了真实车辆性能。所有选中车辆假设仍在比赛。历史进站次数初始假设 0、已用配方仅当前胎，均不冒充历史事实；启用完整赛规前须核实。库存持续为未知/无限数学模型，有限库存只能明确填写。

## 默认预测到底是什么

- 下一完整圈默认 **就是 `prefix_median` 基线**：最近最多 8 个合格已完成圈的中位数，至少 3 个样本；排除首圈与已标记出站圈。它没有学习到优于自身基线的能力。
- 固定 90 秒间距报告默认 **就是 `persistence` 基线**：沿用最后新鲜的有效数值报告。它不是同步物理车距预测。
- 三场等赛事 MAE：圈时中位数 2.634 秒，最近合格圈 2.165 秒、线性 2.571 秒；持续间距 1.957 秒，线性 1.560 秒。准确说法是默认与对应基线完全相同，并在该批目标上劣于这些其他对照方法，不能概括成学习模型“未打败基线”。

它们仍可作为可解释、可复算的参考线，检查数据覆盖、识别状态变化、为研究者提供假设起点。中位数的平滑设计不能当作已经验证的稳定优势；本批变节奏比赛中反而明显滞后。默认方法和原结果未调整。
